# 高品質なビジュアライゼーション（Unreal Engine 連携など）の初期検討（2026-11-06）

位置づけ：構想段階の評価。開発の着手ではない。クラウドのセッションで、コードを読み、公開情報を調べて書いた。Unreal Engine（以下 UE）は動かしていない（GPU も UE も無い環境のため）。

前提（オーナー確認済み）：SketchBRep は**オープンソースで配布しない**。有料（早期アクセス版 1500 円から）、Windows 向け、開発者は少人数。依頼文の「オープンソース CAD」は前提から外す。**売上は UE のロイヤリティの基準（製品の累計 100 万ドル）に届かない見込み**（オーナー確認、2026-11-06）なので、費用は判断の材料にしない。

## 1. 結論（先に）

1. **UE を SketchBRep の中に組み込むのは、今はやらない方がよい。** ロイヤリティは売上の規模からかからない見込みで、費用は問題にならない。それでも、組み込みの難しさ（Qt の画面の中で UE を動かす）、配布物の大きさ（数 GB）、GPU の要件、UE6 への移行の負担が、効果に比べて大きい。
2. 目指す体験（モデリングしながら、表示をリアルに切り替える）は、**2 段構え**で近づける。
   - **SketchBRep の中**：今の表示（OCCT）に「レンダリング表示」を足す。OCCT は PBR（金属感・粗さ）、環境光（IBL）、影、レイトレース・パストレース（光の跳ね返りの計算）を持っている。Rhino の「シェーディング ↔ レンダリング」切替に一番近く、追加の費用も依存も無い。
   - **SketchBRep の外**：Twinmotion や UE を**別のアプリとして**動かし、SketchBRep の変更を**生で送る**（Rhino・SketchUp・Archicad が Twinmotion とやっている Direct Link と同じ形）。UE の実行コードを SketchBRep に入れないので、ロイヤリティの対象になりにくく、UE6 に変わっても送る側は作り直しが小さい。
3. **今やる価値があるのは、エンジンに依存しない下準備だけ。** 材質・照明・カメラ・レンダリング設定を、B-rep とは別の「見た目の情報」として文書に持つこと。どのエンジンを選んでも、UE5 でも UE6 でも無駄にならない。
4. 優先順位：早期アクセス版の発売と、木造・基礎の機能が先。この検討は、発売後に「下準備 → レンダリング表示」から始めるのがよい。

## 2. 今の SketchBRep（表示まわり）

| 項目 | 今の状態 | 場所 |
|---|---|---|
| 表示エンジン | OCCT の 3D ビュー（OpenGL）。既定の照明、4 倍の MSAA（ふちのギザギザ取り） | `src/app/Viewport.cpp` `initViewer` |
| 形の表示 | B-rep を表示用の三角形に分けて描く。精度は「表示品質」で変えられ、正本の形には影響しない（Phase 0 からの方針） | `Viewport`、docs/03 |
| 材質 | 色・透明度・画像（テクスチャ）・**金属感・粗さ・反射率**を文書に保存し、編集画面もある | `src/core/include/sbr/doc/Material.h`、docs/11 |
| 材質の表示 | 色・透明度・画像だけ。**金属感・粗さ・反射率は今は表示に使っていない**（従来の Phong 系の照明） | `Viewport.cpp` の `TexturedFaces` など |
| 影・反射・環境光 | 無し | — |
| 照明 | 文書に照明の情報が無い（ビューの既定の光だけ） | — |
| カメラ | 保存したビュー（シーン）に、視点・注視点・透視／平行を保存 | `doc::Scene` / `CameraState` |
| 書き出し | STEP・IGES・BREP・3DM・STL・COLLADA（.dae）・画像。glTF / USD は無い | docs/32 |
| AI 連携 | MCP・CLI・アプリ内サーバー。変更の差分を読む `get_changes`、ビューの画像 | docs/06 |
| 共有部品 | コンポーネント（同じ形を共有して何度も置く）。木造の部材・金物も共有部品 | docs/14、docs/52 |

ここから言えること：

- **材質の器はもう PBR 向き**（金属感・粗さ）。表示がそれを使っていないだけ。
- **照明・露出・太陽の位置・環境（空の画像）**の情報が無い。ここを足すのが下準備の中心になる。
- 変更を追う仕組み（`get_changes`、オブジェクトの ID）と、外部とやり取りする口（MCP・アプリ内サーバー）があるので、**生で送る**仕組みの土台はある。

## 3. 方式の比較

| 方式 | 内容 | 効果 | 開発の負担 | CAD の軽さへの影響 | ライセンス・費用 | UE6 への耐性 |
|---|---|---|---|---|---|---|
| **A. OCCT のレンダリング表示** | 今のビューに「レンダリング表示」を足す。PBR＋環境光＋影。静止画はパストレースで | 中〜高。ガラス・金属・石・木の質感、影、反射。建築の確認には十分なことが多い。UE の品質（大規模な間接光、植栽、人物など）には届かない | 小〜中 | 切り替えた時だけ重くなる。普段の CAD 表示は今のまま | 追加なし（OCCT は今の部品） | 影響なし |
| **B. 別アプリと生で同期**（Twinmotion / UE） | SketchBRep の変更を、動いている Twinmotion / UE に送り続ける。Datasmith Direct Link（Epic の仕組み）か、自前の UE プラグイン＋SketchBRep のサーバー | 高。UE の表現力をそのまま使える。動画・VR も向こうで | 中〜大。形・材質・照明・カメラの対応づけと、差分の送り方 | SketchBRep 側は、変わった物の三角形を作って送るだけ。重い描画は別のアプリ | SketchBRep は UE のコードを含まない。利用者が自分で Twinmotion / UE を入れる（Twinmotion は年商 100 万ドル未満の会社は無料）。Direct Link の SDK の利用条件は**未確認** | 送る側の形式（シーンの記述）が自前なら、受け側の作り直しだけで済む |
| **C. 交換形式で渡す**（glTF / USD） | ファイルに書き出し、向こうで読み直す。変わったら書き出し直す | 中。どのエンジン・レンダラーでも読める | 小（glTF は OCCT に書き出し機能がある） | 影響なし | 追加なし | 高い（形式が標準） |
| **D. UE を中に組み込む** | SketchBRep のビューの中で UE が描く（UE を部品として埋め込む、または別プロセスの画面を中に映す） | 最高の一体感 | **大**。UE のビルド・配布・更新・GPU の違いへの対応 | 二つの描画エンジンを同時に持つ。メモリ・起動が重い | 製品の累計売上 100 万ドルまではロイヤリティ無し（SketchBRep は届かない見込み）。UE の利用規約（EULA）は守る必要がある。配布物は数 GB 規模 | **低い**。UE6 の早期版は 2027 年後半の見込みと報道されている。UE5 に深く組み込むと移行の負担が大きい |
| **E. ほかのレンダラーを組み込む**（Filament、Cycles など） | 自由なライセンスのレンダラーを中に入れる | 中〜高 | 中〜大。OCCT の表示と二重になる | D と同じ問題が小さく出る | Apache 2.0 など（要確認） | UE と無関係 |

## 4. 落とし穴（どの方式でも）

1. **正本が二つになる。** UE / Twinmotion 側で形や材質を直すと、SketchBRep に戻らない。**向こうで直すのは見た目の追加（植栽・人・家具・ポスト処理）だけ**、形と材質の正本は SketchBRep、と最初に決める。
2. **三角形の質。** B-rep を三角形にする時の細かさ・法線・UV（画像の貼り方）が、リアルな表示では目立つ（曲面のカクカク、画像の伸び）。CAD 表示より細かい三角形を、送る時だけ作る仕組みが要る。正本の精度は変えない。
3. **ID が変わる。** 差分で送るには、物の ID が編集で変わらないことが要る。押し出しやブーリアンで面が作り直されると、面の単位の材質がずれやすい。今の材質の割り当て（面・物）の仕組みを、そのまま使えるか要確認。
4. **単位と座標の向き。** SketchBRep は mm・Z 上。UE は cm・Z 上・**左手系**。変換を一か所にまとめる。
5. **共有部品の扱い。** 木造の部材・金物は数千個になる。共有部品を、向こうでも**インスタンス**（同じ形を使い回す）として送らないと重くなる。
6. **CAD だけの状態。** 断面、非表示、X 線表示、選択、編集中のグループ。どれを向こうに反映するかを決める。
7. **GPU の要件。** レイトレース・UE は良い GPU が要る。CAD としての最低の要件（今は OpenGL 3.3）は上げない。高品質表示は「動く PC だけの追加機能」にする。
8. **ライセンスは変わる。** UE・Twinmotion の条件は 2024 年に大きく変わり、2026 年にも Unreal サブスクリプションの内容が変わった（Twinmotion が外れる）と告知されている。採用の前に、その時点の公式の条件を確かめる。

## 5. UE5 で今から確かめること・UE6 を見て決めること

**UE5 で（ローカルの PC で）確かめること**（どれも小さな試作でよい）

- 自前の小さな UE プラグインが、SketchBRep のアプリ内サーバーから**変わった物だけ**受け取って、描き直せるか。送るのは三角形・材質・変換・インスタンス。1,000〜5,000 個の部材で、1 回の変更が何秒で向こうに出るか。
- Datasmith Direct Link を、自前のアプリから使えるか（SDK の入手方法と利用条件）。使えれば Twinmotion にもそのまま送れる。
- 材質の対応：SketchBRep の（色・金属感・粗さ・反射率・透明度・画像）を UE の標準の材質に写した時の見え方。ガラス・金属・石・木で。
- 単位と座標の変換、共有部品のインスタンス化。

**UE6 を見て決めること**

- UE を中に組み込むか（方式 D）。UE6 の早期版（報道では 2027 年後半）の、組み込み・ライセンス・配布の形が分かってから。
- UE6 で、外とのやり取りの標準（USD など）がどうなるか。それに合わせて、送る形式を Datasmith か USD か選ぶ。

## 6. おすすめの段階

| 段階 | 内容 | 負担 | いつ |
|---|---|---|---|
| 0. 下準備（エンジンに依存しない） | 文書に「見た目の情報」を足す：照明（太陽＝日時と場所から、点・スポット・面光源）、環境（空の画像、明るさ）、カメラのレンズ・露出、レンダリングの設定。材質は今のまま（PBR の項目はある）。**保存・Undo・AI のコマンドは、ほかの編集と同じ経路** | 小 | 発売後すぐ |
| 1. レンダリング表示（OCCT） | 表示の切り替え：今の CAD 表示 ／ リアル表示（PBR＋環境光＋影）／ 静止画（パストレース）。リアル表示では選択・スナップを止めない。静止画は「レンダリング」ボタンで計算して保存 | 中 | 段階 0 の後 |
| 2. glTF の書き出し | 見た目の情報ごと書き出す（OCCT の glTF 書き出しを使う）。どのレンダラーでも読める | 小 | 段階 1 と並行でよい |
| 3. 外部と生で同期 | 自前の UE プラグイン、または Direct Link。送る側は「変わった物の三角形・材質・変換」を、アプリ内サーバーから流す | 中〜大 | 需要が見えてから |
| 4. 組み込みの再検討 | UE6 の情報が揃ってから、方式 D が要るか判断 | — | 2027 年以降 |

AI（MCP）との関係：段階 0 で、材質・照明・カメラ・表示の切り替えのコマンドを、ほかの編集と同じ形で足す。AI がビューの画像を読む仕組みは今もあるので、段階 1 のリアル表示をそのまま AI に見せられる。

## 7. 今の優先順位との関係

- 今は、早期アクセス版の発売（利用規約・実機の確認）と、木造・基礎の機能（docs/52〜80）が先。
- この検討で**今すぐ**やるのは、文書（この評価）を残すことだけ。段階 0 は発売後の最初の候補。
- 依頼文の「守りたい思想」（B-rep が正本、表示用の三角形が精度や編集を縛らない、高品質表示が無くても CAD として成り立つ、Undo・選択・スナップを犠牲にしない、AI から操作できる、特定のエンジンに寄りかからない）は、段階 0〜3 の形ならすべて守れる。方式 D（組み込み）だけが、軽さとエンジン依存の点で衝突しやすい。

## 8. まだ確かめていないこと

- Datasmith Direct Link を、Epic 以外のアプリが組み込む時の SDK の入手方法・利用条件（公開情報で見つからなかった）。
- 自前の UE プラグインや、UE を組み込んだアプリを配る時の、EULA 上の細かい条件（表示の義務、配布できるファイルなど）。ロイヤリティは売上の規模からかからない見込み。
- UE6 の時期・中身は、報道ベース（Epic の正式な発表文は今回見つけられなかった）。
- OCCT のパストレースの速さ・画質を、オーナーの PC（Windows、表示倍率 175%）の GPU で試していない。
- Twinmotion が 2026-05-27 から Unreal サブスクリプションに含まれなくなったという告知の詳細。
