# 10. 性能：計測と大規模モデルへの道筋

目標は「大きな建築モデルでも、SketchUp のように軽く触れる」こと。
正規形状（B-rep）は粗くせず、**仕事の量を変更の大きさに比例させる**（1 部材の編集で建物全体を作り直さない）ことで達成する。
将来 GPU に処理を渡せるよう、データの持ち方も合わせて設計する。

## 計測のしかた

| 道具 | 内容 |
|---|---|
| `sbr_bench [--sizes 250,500,1000] [--json out.json]` | ヘッドレス。`instances`（1 つの部品定義を N 個配置）と `unique`（共有なしの箱 N 個）を作り、検索・ワールド配置・スナップ索引・スナップ照会・1 部材の移動と Undo・`list_objects`・保存を計測 |
| `SBR_BENCH_N=1000 sbr_gui_tests benchViewportSync` | 画面あり。初回同期、1 部材を動かした後の同期、選択、描画 1 回を計測（通常の CI では skip） |

N を倍にしたときの伸び方（線形か二乗か）を見るのが主目的。数字は**この環境（4 コア Xeon 2.8 GHz・Xvfb のソフトウェア描画）での実測**で、製品目標ではない。

## 第 1 段：索引と増分同期（実装済み）

| 変更 | 内容 |
|---|---|
| Document の索引 | ID → 位置、親 → 子 をハッシュで保持（遅延再構築、末尾追加は差分更新）。`find` / `children` / `worldTransform` が O(1) / 親の段数 |
| 変更ログ | `insert` / `replace` / `remove` ごとに連番。`changedSince(seq)` で「前回以降に変わった ID」を取得。設定変更・全消去は全体の再同期を指示 |
| スナップ索引のキー化 | `InferenceEngine::setShape(key, shape)` / `removeShape`。変わった形状だけ索引し直す。面の交差器は外接箱が視線に掛かったものだけ遅延生成 |
| Viewport の増分同期 | 変更ログの ID（＋変わったグループの子孫）だけ表示・スナップを更新。色・透明度が変わった物だけ再表示（以前は毎回全部）。選択は「入った物・抜けた物」だけ再着色 |
| 描画の集約 | `redraw()` は再描画の予約（1 イベントで 1 フレーム）。即時描画は `renderNow()` |
| プロパティパネル | ツリーはドキュメントが変わったときだけ作り直し、選択だけなら強調を移すだけ |

### 計測結果（instances、2000 配置）

| 操作 | 前 | 後 |
|---|---|---|
| 全 ID の検索（core） | 12.8 ms（N² で増加） | 0.13 ms |
| 全オブジェクトのワールド配置（core） | 10.3 ms | 0.6 ms |
| スナップ索引の全体構築（core） | 324 ms | 77 ms |
| スナップ照会 1 回（core） | 14.5 ms | 1.7 ms |
| 1 部材を動かした後の画面同期（描画除く） | 745 ms（描画込み） | 1.9 ms |
| 選択（ウィンドウ全体） | 861 ms | 16 ms |
| GUI テスト一式 | 約 72 s | 約 33 s |

## 第 2 段（着手済み）：定義単位の表示共有

同じ部品定義の配置は、ローカルの正規形状（TShape）が同じ。表示コピーとテッセレーションをその形状につき 1 つだけ作り、各配置はそれに配置（Location）を付けるだけにした。三角形データは共有されるので、配置が増えても複製・メッシュ生成は増えない。定義を編集すると新しい形状の表示コピーに切り替わり、古いものは使う配置がなくなった時点で解放される。

| 操作（instances 2000 配置） | 前 | 後 |
|---|---|---|
| 初回同期（開いた直後） | 約 3.4 s | 約 0.73 s |

次は AIS_ConnectedInteractive で表示構造（presentation）自体も共有し、その後、実 GPU で描画コストを計測してから instancing（配置行列の配列を GPU に渡して 1 回で描く）に進む。

## 第 3 段（実装済み）：局所スナップ

スナップ索引の各形状の外接箱で範囲階層（BVH）を作り、照会では「カーソルの近く（箱の 8 隅を画面に投影した範囲＋許容ピクセル）」「視線・ピック線が通る」箱だけを辿る。最終判定は従来どおり正規 B-rep の点・辺・面で行うので精度は変わらない。透視投影ではカメラの向き（`SnapQuery::viewDirection`）を使い、視点より後ろに掛かる箱は捨てない（保守的）。

| instances | スナップ照会 1 回（前 → 後） | 1 形状更新＋照会（BVH 再構築込み） |
|---|---|---|
| 1,000 | 8.5 ms → 0.10 ms | 1.3 ms |
| 4,000 | 27 ms → 0.17 ms | 3.0 ms |
| 16,000 | （未計測） → 0.5 ms | 18 ms |

BVH は変更後の最初の照会で作り直している（O(N log N)）。10 万規模では部分更新（refit）に替える。

## AI 向けの読み取り経路（実装済み）

| 命令（instances 4,000 配置） | 時間 |
|---|---|
| `list_objects`（全件・全項目） | 70 ms |
| `query_objects`（ID だけ・最大 5,000 件） | 6.6 ms |
| `aggregate`（種類ごとの集計） | 0.5 ms |

体積・面積・外接箱は局所形状ごとにキャッシュ（必要な値だけ計算）。共有なしの 1,000 形状では、初回の `list_objects` は体積計算が支配的（約 0.7 s）、2 回目以降は軽い。

## 保存・読み込み（実装済み）

- **形状の共有保存（形式 3）**：同じ形状（部品の配置）は `shapes` 表に 1 回だけ書き、オブジェクトは番号で参照。読み込み後も同じ形状を共有するので、開き直しても表示共有が効く。形式 1・2 も読める
- **保存後の確認を軽く**：書いたファイルを読み戻して構造と形状を確認するが、レシピの再実行はしない（読み込み時の役目）
- **開くのは速く、確認は後で**：アプリで開くときは保存された形状だけで表示し、レシピの再生成・照合はアイドル時に 15 ms ずつ（部品定義は 1 回だけ）。食い違いはステータスバーに件数、ツールチップに内容。`sbr_cli` / API の `open` は従来どおり全部照合（配置は形状の組ごとに 1 回）

| 操作 | 前 | 後 |
|---|---|---|
| 保存（instances 4,000） | 10.4 s・13 MB | 0.15〜0.21 s・2.1 MB |
| 読み込み・全照合（instances 4,000） | 5.9 s | 0.11 s |
| アプリで開く（unique 1,000） | 4.4 s | 0.14 s（照合は後から） |

## まだ重いところ（次の段の対象）

| 項目 | 2000 配置での実測 | 原因 | 次の対策 |
|---|---|---|---|
| 初回同期（開いた直後） | 約 0.73 s（共有前 3.4 s） | 配置ごとに表示オブジェクトと面・辺の対応表を作る | presentation の共有 |
| 描画 1 フレーム | 約 50〜70 ms（ソフトウェア描画） | 配置ごとに別の表示オブジェクト | 第 2 段＋GPU instancing（実 GPU では大幅に軽いはず。要実機計測） |
| BVH の再構築 | 16,000 で 18 ms／編集 | 変更のたびに全体を作り直す | 部分更新（refit）、配置と定義の 2 段構成 |
| 共有なしの形状の保存・全照合の読み込み | unique 4,000 で保存 4.3 s・照合 17 s | 形状ごとの BRep 文字列化・体積と厳密外接箱での照合 | 文字列化の並列化、照合を形状の署名（面・辺の数など）で軽く |
| `list_objects` の初回（共有なし） | 1,000 形状で約 0.7 s | 体積の厳密計算 | 必要な時だけ `query_objects` の `fields` で取る運用、計算の非同期化 |

## GPU を見据えたデータ設計

1. **形と置き場所を分ける**：部品定義の形は 1 つ、配置は 4×4 行列＋可視性・色だけ。GPU instancing（1 回の命令で同じ形を大量に描く）にそのまま渡せる
2. **連続配列で持つ**：表示・スナップ用の頂点・辺・外接箱・配置行列は、オブジェクトごとの散らばったデータでなく連続配列へ寄せる（GPU への一括転送・CPU キャッシュにも効く）
3. **変更の差分を 1 回で知らせる**：変更ログ／変更セットが「どこを GPU に送り直すか」の単位になる
4. **粗く探して正確に決める**：候補の絞り込み（視錐台・範囲階層）は GPU に任せられる。最終的なスナップ・選択は正規 B-rep で CPU が確定するので、精度は落ちない
5. **重い幾何演算は編集の通り道から切り離す**：将来は別スレッド／別プロセスで計算し、確定だけを短く行う

## グループ・コンポーネント編集の出入り（2026-10-24）

実機の報告：コンポーネントやグループを数千個コピーしたモデルで、編集に入る・出ると何秒も止まる（固まってはいない）。

**原因**（`benchEnterManyCopies`、コピー 1500 個ずつ・計 4563 オブジェクト）
- 入る：編集中以外のものを薄く表示するとき、全オブジェクトの表示（presentation）を作り直していた。変わるのは透明度だけ。
- 出る：コアの処理は 20 ms。残りは画面の更新で、全配置の形が新しい定義に変わるため、配置ごとに表示を作り直す（1 個あたり約 0.2 ms。内訳は表示計算 0.13 ms、スナップ用の索引 0.06 ms など）。

**対策**
- 透明度だけが変わるときは、表示を作り直さず見た目の設定だけを変える（`SetTransparency` が計算済みの表示に反映する）。X 線の切り替えも同じ。
- 画面の更新を、約 50 ms ずつに分けて行う（`Viewport::syncSlice`）。合間にイベントを処理するので、カーソルや入力は止まらない。
  - 選択の色や、変わったオブジェクトを先に処理する。
  - まだ更新されていない配置は、古い形のまま表示・スナップされる。その配置が更新されると、新しい形になる。
  - ファイルを開いたときや画像書き出しなど、まとめて済ませたい場面は今までどおり一度に行う（`syncNow`）。

**計測**（ms、Linux CI と同じ構成の仮想ディスプレイ）

| 操作 | 前 | 後 |
|---|---|---|
| コンポーネント編集に入る | 552 | 67〜75 |
| グループに入る | 444 | 28〜79 |
| グループから出る | 401 | 25〜67 |
| コンポーネント編集から出る（最初の応答まで） | 994 | 約 80（コア 20 + 最初の更新 57）。残りの約 560 は少しずつ |

- テスト：`groupEditFadesTheRest`（薄く表示され、出ると元の色に戻ることを画面の色で確認）、`componentEditUpdatesPlacementsInSlices`（600 配置で、最後には全配置が新しい形になり、選べる）。
- 残り：出たあとの全配置の更新そのもの（合計時間）は変わらない。配置ごとの表示を共有する（GPU instancing）のが次の段。

## 大量コピーでの日常操作（2026-10-24）

実機の報告（コンポーネントやグループを数千個コピーすると重い）を受けて、日常の操作をまとめて測り直し、遅いところを直した。

**計測**：`benchManyCopiesOperations`（`SBR_BENCH_N=800`）。窓 3 つ付きの壁パネルのコンポーネント 800 配置と、箱のグループ 800 個。全 2436 オブジェクト。表示の更新が終わるまでの時間（ms）。

| 操作 | 前 | 後 | 主な原因 |
|---|---|---|---|
| 最初の表示 | 2459 | 1124 | 新しい表示を 1 回作った直後に、もう一度作り直していた。クリック判定用のデータも 2 回計算していた |
| 全選択 | 2098 | 336 | 選択の色を変えるたびに表示を作り直していた。選択中かどうかの判定が「選択数 × オブジェクト数」回のループだった。選択ドットを配置ごとに作っていた |
| 選択解除 | 1057 | 49 | 同上 |
| 全部移動 | 3135 | 427 | 位置が変わっただけでも表示を作り直していた |
| 移動の Undo | 3079 | 210 | 同上 |
| 半分コピー | 2154 | 943 | 新しい表示の作成（下の「残り」を参照） |
| コピーの Undo | 1297 | 94 | 1 個消すたびに、文書全体の検索表（ID → 位置）を作り直していた |
| 半分削除 | 1534 | 217 | 同上 |
| 削除の Undo | 3308 | 1002 | 同上と、新しい表示の作成 |
| 開く | 3373 | 1766 | 新しい表示の作成。読み込みそのものは 60 ms |

**直したこと**
- 表示
  - 色・選択・透明度の変更は、計算済みの表示の見た目の設定だけを変える。新しいオブジェクトは見た目を決めてから表示するので、表示の計算は 1 回だけ。
  - クリック判定用のデータは、今のツールが使う種類だけを最初から計算する。
  - 選択中かどうかはセットで引く。コンポーネントの配置の選択ドットは、配置どうしで 1 つの表示を共有する（`AIS_ConnectedInteractive`）。
  - 移動しただけのオブジェクト（形はそのまま、回転・平行移動だけ）は、表示を作り直さずに置き場所だけを変える。クリック判定・強調表示・テクスチャ・移動中のプレビューも、その置き場所に合わせる。
- 文書
  - Undo / Redo で、削除・追加・置き換えを種類ごとにまとめて適用する。検索表の作り直しは、まとめごとに 1 回だけ。グループ化（親の変更）では位置の表を保つ。
- 吸着
  - 点と辺の登録は、カーソルが近づいたときに初めて行う（追加時は外枠だけ）。
  - ガイド線（通り芯）と辺の交点は、ガイド線が通る範囲のものだけを調べる。
- パネル
  - オブジェクトの一覧は、変わった行だけを書き換える。数千行の選択も、再描画は 1 回だけ。

**テスト**
- `movedObjectsPickWhereTheyAre`：動かしたもののクリック判定・吸着・強調表示が新しい位置にあること。Undo で戻ること。
- `selectionDotsOnOnePlacementOnly`：選んだ配置だけにドットが付き、外せば消えること。
- 既存の GUI テスト 122 件、コアのテスト 292 件。

**残り（次の段）**
- 新しいオブジェクトの表示作成に、1 個あたり約 0.4 ms かかる（表示の計算と、クリック判定の計算）。同じ形のコピーでも、表示はそれぞれが持っている。
- 配置ごとの見た目（色・選択・薄く表示）を保ったまま表示を共有する仕組み（GPU instancing）か、クリック判定の計算をカーソルが近づいたときに行う仕組みが、次の候補。

## ほかの遅くなるパターンの検証（2026-10-24）

`benchMoreSlowPatterns`（`SBR_BENCH_N=500`）で測った。モデルの中身：
- 窓付きパネル 500 配置
- バラの箱 500 個
- 平行な線 1000 本
- 窓 60 個の長い壁

あわせて 2016 オブジェクト。表示の更新が終わるまでの時間（ms）。

| 操作 | 前 | 後 | 原因 |
|---|---|---|---|
| 線ツールでマウスを 100 回動かす（吸着） | 27081 | 400〜500 | 点を画面に投影するたびに、ビューの大きさをウィンドウシステムに問い合わせていた（X11 では往復通信）。吸着 1 回で数千回 |
| 範囲選択（全体を囲む。面と辺 11000 個） | 12966 | 1042〜1122 | 同上。コンポーネント 1 つごとに正確な外枠を計算していた。選択の照合がリストの総当たりだった。パネルの更新が 2 回あった |
| 交差選択 | 6966 | 300〜350 | 同上 |
| タグを表示に戻す（500 個） | 1066 | 276 | 非表示にすると表示を捨てていて、戻すと全部作り直していた |
| 窓 60 個の壁の上面を押し出す | 2228 | 1304 | 壁に手を加えるたびに、「壁 − 窓 60 個」の Boolean をやり直していた |

**窓をまとめて開ける（`place_openings`）**：長さ 60 m の壁、CLI で計測（秒）

| 窓の数 | 前 | 後 |
|---|---|---|
| 10 | 3.1 | 0.15 |
| 20 | 22.4 | — |
| 40 | 216.3 | 1.15 |
| 80 | 300 秒以上 | 2.1 |
| 200 | （測れず） | 6.1 |

- 原因
  - 窓を 1 つずつ押し通していた。窓 1 つごとに、穴の増えていく壁全体の Boolean を計算していた。
  - その壁を、毎回最初の箱から作り直していた。
  - さらに Boolean も、道具（引く形）を 1 つずつ順番に処理していた。
- 対策
  - 窓をすべて 1 つの Subtract の道具にする。レシピは押し通しと同じ形なので、一覧やサイズ変更はこれまでどおり使える。
  - Boolean は道具をまとめて 1 回で処理する。入力は書き換えない（非破壊モード）。
  - 入れ子のレシピ（共有されていて変わらないもの）の形と、Boolean の結果を覚えておく。
  - 既存の窓 40 個の壁に窓を 1 つ足すと 0.4 秒。

**ファイルを開いたあとのレシピ確認**
- 確認は別のスレッドで行う（ドキュメントの写しを使う）。窓の多い壁の確認で、画面が止まっていた。
- `openingKeepsTheWindowResponsive`：窓 40 個の壁 5 枚の確認（3.7 秒）の間も、画面が止まったのは最長 82 ms。

**そのほか測ったもの**（問題なし、ms）
- 線 1000 本を横切る線：124〜162
- 別の場所の線：128〜162
- X 線のオン・オフ：130〜183
- 隠す・すべて表示：186〜284
- 500 個のグループ化・解除：168〜250
- 大きなグループに入る・中に線・出る：160〜230
- 300 個をコンポーネントにする：770〜1150
- 分解：270〜410

**テスト**
- `shownAgainPicksAndSnaps`：非表示から戻したものを選べて、吸着でき、押し出せること。隠している間に動かしたものが、新しい位置に出ること。
- `openingKeepsTheWindowResponsive`
