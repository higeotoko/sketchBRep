# 10. 性能：計測と大規模モデルへの道筋

目標は「大きな建築モデルでも、SketchUp のように軽く触れる」こと。
正規形状（B-rep）は粗くせず、**仕事の量を変更の大きさに比例させる**（1 部材の編集で建物全体を作り直さない）ことで達成する。
将来 GPU に処理を渡せるよう、データの持ち方も合わせて設計する。

## 計測のしかた

| 道具 | 内容 |
|---|---|
| `sbr_bench [--sizes 250,500,1000] [--json out.json]` | ヘッドレス。`instances`（1 つの部品定義を N 個配置）と `unique`（共有なしの箱 N 個）を作り、検索・ワールド配置・スナップ索引・スナップ照会・1 部材の移動と Undo・`list_objects`・保存を計測 |
| `SBR_BENCH_N=1000 sbr_gui_tests benchViewportSync` | 画面あり。初回同期、1 部材を動かした後の同期、選択、描画 1 回を計測（通常の CI では skip） |

N を倍にしたときの伸び方（線形か二乗か）を見るのが主目的。数字は**この環境（4 コア Xeon 2.8 GHz・Xvfb のソフトウェア描画）での実測**で、製品目標ではない。

## 第 1 段：索引と増分同期（実装済み）

| 変更 | 内容 |
|---|---|
| Document の索引 | ID → 位置、親 → 子 をハッシュで保持（遅延再構築、末尾追加は差分更新）。`find` / `children` / `worldTransform` が O(1) / 親の段数 |
| 変更ログ | `insert` / `replace` / `remove` ごとに連番。`changedSince(seq)` で「前回以降に変わった ID」を取得。設定変更・全消去は全体の再同期を指示 |
| スナップ索引のキー化 | `InferenceEngine::setShape(key, shape)` / `removeShape`。変わった形状だけ索引し直す。面の交差器は外接箱が視線に掛かったものだけ遅延生成 |
| Viewport の増分同期 | 変更ログの ID（＋変わったグループの子孫）だけ表示・スナップを更新。色・透明度が変わった物だけ再表示（以前は毎回全部）。選択は「入った物・抜けた物」だけ再着色 |
| 描画の集約 | `redraw()` は再描画の予約（1 イベントで 1 フレーム）。即時描画は `renderNow()` |
| プロパティパネル | ツリーはドキュメントが変わったときだけ作り直し、選択だけなら強調を移すだけ |

### 計測結果（instances、2000 配置）

| 操作 | 前 | 後 |
|---|---|---|
| 全 ID の検索（core） | 12.8 ms（N² で増加） | 0.13 ms |
| 全オブジェクトのワールド配置（core） | 10.3 ms | 0.6 ms |
| スナップ索引の全体構築（core） | 324 ms | 77 ms |
| スナップ照会 1 回（core） | 14.5 ms | 1.7 ms |
| 1 部材を動かした後の画面同期（描画除く） | 745 ms（描画込み） | 1.9 ms |
| 選択（ウィンドウ全体） | 861 ms | 16 ms |
| GUI テスト一式 | 約 72 s | 約 33 s |

## 第 2 段（着手済み）：定義単位の表示共有

同じ部品定義の配置は、ローカルの正規形状（TShape）が同じ。表示コピーとテッセレーションをその形状につき 1 つだけ作り、各配置はそれに配置（Location）を付けるだけにした。三角形データは共有されるので、配置が増えても複製・メッシュ生成は増えない。定義を編集すると新しい形状の表示コピーに切り替わり、古いものは使う配置がなくなった時点で解放される。

| 操作（instances 2000 配置） | 前 | 後 |
|---|---|---|
| 初回同期（開いた直後） | 約 3.4 s | 約 0.73 s |

次は AIS_ConnectedInteractive で表示構造（presentation）自体も共有し、その後、実 GPU で描画コストを計測してから instancing（配置行列の配列を GPU に渡して 1 回で描く）に進む。

## 第 3 段（実装済み）：局所スナップ

スナップ索引の各形状の外接箱で範囲階層（BVH）を作り、照会では「カーソルの近く（箱の 8 隅を画面に投影した範囲＋許容ピクセル）」「視線・ピック線が通る」箱だけを辿る。最終判定は従来どおり正規 B-rep の点・辺・面で行うので精度は変わらない。透視投影ではカメラの向き（`SnapQuery::viewDirection`）を使い、視点より後ろに掛かる箱は捨てない（保守的）。

| instances | スナップ照会 1 回（前 → 後） | 1 形状更新＋照会（BVH 再構築込み） |
|---|---|---|
| 1,000 | 8.5 ms → 0.10 ms | 1.3 ms |
| 4,000 | 27 ms → 0.17 ms | 3.0 ms |
| 16,000 | （未計測） → 0.5 ms | 18 ms |

BVH は変更後の最初の照会で作り直している（O(N log N)）。10 万規模では部分更新（refit）に替える。

## まだ重いところ（次の段の対象）

| 項目 | 2000 配置での実測 | 原因 | 次の対策 |
|---|---|---|---|
| 初回同期（開いた直後） | 約 0.73 s（共有前 3.4 s） | 配置ごとに表示オブジェクトと面・辺の対応表を作る | presentation の共有 |
| 描画 1 フレーム | 約 50〜70 ms（ソフトウェア描画） | 配置ごとに別の表示オブジェクト | 第 2 段＋GPU instancing（実 GPU では大幅に軽いはず。要実機計測） |
| BVH の再構築 | 16,000 で 18 ms／編集 | 変更のたびに全体を作り直す | 部分更新（refit）、配置と定義の 2 段構成 |
| 保存 | 約 5.3 s | 保存後の読み戻し検証で全レシピを再生成、配置ごとに BRep を書く | 検証の軽量化、定義単位の保存 |
| `list_objects` | 64 ms（unique 1000 で 0.8 s） | 全件の体積・外接箱を毎回計算 | AI 向けの検索・フィールド指定・計測値キャッシュ |

## GPU を見据えたデータ設計

1. **形と置き場所を分ける**：部品定義の形は 1 つ、配置は 4×4 行列＋可視性・色だけ。GPU instancing（1 回の命令で同じ形を大量に描く）にそのまま渡せる
2. **連続配列で持つ**：表示・スナップ用の頂点・辺・外接箱・配置行列は、オブジェクトごとの散らばったデータでなく連続配列へ寄せる（GPU への一括転送・CPU キャッシュにも効く）
3. **変更の差分を 1 回で知らせる**：変更ログ／変更セットが「どこを GPU に送り直すか」の単位になる
4. **粗く探して正確に決める**：候補の絞り込み（視錐台・範囲階層）は GPU に任せられる。最終的なスナップ・選択は正規 B-rep で CPU が確定するので、精度は落ちない
5. **重い幾何演算は編集の通り道から切り離す**：将来は別スレッド／別プロセスで計算し、確定だけを短く行う
