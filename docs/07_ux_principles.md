## 0. 文書の位置づけと、開発エージェントへの最重要指示

本書は機能を増やすためのToDoリストではない。**これから追加する全機能が、同じ操作思想を持つための判断基準**である。具体的な実装に着手する前に、既存仕様との整合性を確認し、観察できるユーザー体験・機械的に検証できる受け入れ条件・失敗時の挙動を定めること。

**必須（MUST）**：破ってはならない製品原則。既存コードとの衝突がある場合は勝手に変更せず、衝突と選択肢を明示する。  
**推奨（SHOULD）**：例外には理由と代案が必要。  
**任意（MAY）**：後続フェーズで選択できる。

AI開発エージェントは本書を読んでも、即座に大規模なリファクタリングや一括機能実装をしてはならない。まず現行コードと比較した**ギャップ分析 → 提案する最小変更 → 回帰テスト設計 → 依存順の実装計画**を出すこと。現在ある良い設計は壊さない。

### 0.1 いま守るべき実装資産

- `src/core`がQtに依存せず、`doc::Modeler`をGUIと`api::CommandApi`／MCPが共通利用する。
- 正規形状はOCCT BRep、表示用テッセレーションはコピー上で行う。**表示メッシュは設計ジオメトリの正本ではない**。
- `Recipe`により基本形状と編集意図をできる限り保持し、再生成・パラメータ再編集できる。
- 失敗時は無変更、Undo/Redoは確定済みコマンド単位。AI `batch` は既定で原子的。
- mm／度、Z上方向。スナップは正規形状から計算し、画面上での近傍判定を行う。
- Windows／Linuxを対象としたCIと、GUI・コマンド・MCPのテスト資産がある。
- 現行の寸法・テキスト・シーン・円弧・NURBS曲線・ロフト／スイープなど、すでに実装した機能を「未実装」と誤認して作り直さない。

本書はこれらの設計の**上にUX規範を積む**。内部エンジンの刷新を指示するものではない。

## 1. 北極星：操作の摩擦を最小化する

### 1.1 成功の定義

建築デザイナーが「ここに壁を立てたい」「ここに開口を設けたい」「この軒先を伸ばしたい」と思った時、

1. 目的の形を画面で**直接指せる**。
2. カーソル移動とプレビューで、操作の方向と結果を**確定前に予測できる**。
3. 必要なら**操作途中・確定直後に寸法を指定できる**。
4. 成功時は**破綻のない形状**として残り、変更履歴に復元可能な状態が記録される。
5. 失敗時は形状を壊さず、**なぜ失敗したか／次にどうすればよいか**が分かる。
6. GUIであってもAIであっても、同じ編集規則を守る。

**UX上の成功とは「コマンドが呼べた」ではなく、「意図した編集が少ない認知負荷で完了し、次の設計思考に戻れる」ことである。**

### 1.2 何を模倣し、何を模倣しないか

SketchUpから継承するのは、Push/Pull、推論、直接選択、操作中の数値入力、線と面の連続性、ツール切替の少なさ、視点移動の軽快さという**操作の文法**である。

模倣しないのは、ポリゴン分割を正規ジオメトリとする内部構造、曲面がファセットに制限される仕様、形状破壊を当然視する編集、拡張性を損なうショートカット依存など。ブランド固有のアイコン／ビジュアルを再現する必要もない。

Rhino/OCCTからは数学的に正確な曲線・曲面・ソリッド、トポロジー検証、入出力の信頼性を採る。一方、ユーザーに毎回トリム、サーフェス選択、ブーリアン種別を強制してはならない。

### 1.3 守るべき設計原則（優先順）

| ID | 原則 | 具体的な意味 | 禁止する悪化例 |
|---|---|---|---|
| P-01 | **直接性** | 見えている面・稜線・点をその場でつかみ、操作する | 原則としてIDやツリーを調べなければ編集できない |
| P-02 | **描画と編集の連続性** | 線を描いて閉じれば面、面を動かせば形が変わる | 都度「面生成」「編集対象変換」を要求する |
| P-03 | **意図の推論** | 端点、軸、平行、面上等を先読みして候補を示す | 根拠の見えない吸着、頻繁な候補の飛び移り |
| P-04 | **ラフから正確へ** | マウスで仮決めし、数値で確定・修正できる | 作業前に座標・拘束・数値ダイアログ必須 |
| P-05 | **予測可能性** | 実行前に編集結果が理解できる | 確定後に初めて大きく違う形になる |
| P-06 | **非破壊性・可逆性** | レシピ・Undo・ロールバックで編集を守る | 失敗時に形が半端に残る、Undoが曖昧 |
| P-07 | **階層の透明性** | グループ／部材／面の区別が直感的 | コンテキスト外を意図せず編集する |
| P-08 | **連続した思考** | 選択・カメラ・数値入力を無駄に遮らない | 毎手のモード切替・パネル往復・待ち時間 |
| P-09 | **複雑さの段階的開示** | 基本操作は短く、専門操作は必要時に出す | 初心者にBRepの内部階層を露出する |
| P-10 | **操作経路の平等性** | GUI／AI／CLIは同じモデル意味論を共有 | AI専用の簡略処理がGUIと違う結果を作る |

**衝突時の裁定**：正規形状の妥当性とデータ保全（P-06）が最優先。その範囲内で直接性・即応性を最大化する。実現不能な操作を「成功したように見せる」ことは禁止。

## 2. すべてのツールに共通する操作契約（Interaction Contract）

### 2.1 共通状態と意味

| 状態 | ユーザーに見えるもの | モデルに対する約束 |
|---|---|---|
| `Idle` | ホバーによる対象強調、候補ヒント | ドキュメント無変更 |
| `Armed` | 始点・対象・基準軸を固定。次に必要な入力を明示 | 原則無変更 |
| `Preview` | ゴースト、寸法、ガイド、スナップ情報 | 正規ドキュメントには未確定変更を残さない |
| `Commit` | 妥当性検証、編集結果反映 | **成功した操作のみ**履歴に記録 |
| `RecentEdit` | 直前の操作の数値再入力を受け付ける | 上書き再編集の意味を一貫させる |
| `Error/Cancel` | 原因と復帰方法を提示 | キャンセル・失敗で確定済み形状を変更しない |

`Tool`固有の必要ステップは認めるが、上記のユーザーへの契約は一致させる。

### 2.2 共通イベント仕様

- **クリック**：現在のツールが必要とする対象／基準を確定。確定タイミングをステータスヒントとカーソルで示す。
- **マウス移動**：可能な限りプレビュー更新のみ。高負荷処理は中断・遅延・粗いプレビューへの切替を許すが、静かに最終形状を改変してはならない。
- **文字入力**：フォーカスを数値ボックスへ移す必要なく寸法に反映（テキスト注記等の文字編集状態では例外）。
- **Enter**：現在段階の数値／形状を確定。入力途中で不正なら確定せず、その理由を表示。
- **Esc**：1回目で入力途中／現在段階を取り消し、元の有効状態へ。グループ編集の終了等と衝突する場合は現在の入力取消を優先。履歴にキャンセル操作を積まない。
  - **実装済み（全ツール共通）**：Esc は段階を 1 つだけ戻す。複数段のツールは段ごと（円弧・寸法：終点→始点、回転：角度→基準→中心、回転体：軸の 2 点目→1 点目→面選び、尺度）、点を連ねるツールは最後の点を 1 つ取り消す（曲線・壁・スラブ）。戻す段がなければ入力を取り消すだけで、何も作らず履歴にも積まない
  - **例外は線ツールだけ**：SketchUp と同じく Esc で連続線を終え、クリックした分は残す（線を止める手癖を優先）
  - カメラ操作（オービット・パン・ズーム）は入力途中の状態を消さない（テスト `escStepsBackAndConstraintsShow`）
- **今かかっている固定の表示（実装済み）**：ステータスバーの青い文字で「対象: … ｜ 作業面: 地面 ／ 高さ 3000 の水平面 ／ X 方向を向いた縦の面 ｜ 方向: X 軸（赤）に固定（↓で解除）」を常に表示。矢印キー・Shift のロック、面の上で描き始めた作業面、プッシュ/プル・移動・回転・開口の対象が分かる。何も固定されていなければ消える
- **Ctrl+Z/Redo**：ユーザーが認識する1つの操作意図＝原則1履歴単位。AIのatomic batchもこれに準じる。
- **カメラ操作**：作図の途中でも視点を動かせ、継続可能。確定済み基準点や現在の入力値を消してはならない。
- **修飾キー**：押下中／トグル／確定後追加入力という性質をツール間で統一し、表示する。

### 2.3 画面フィードバックの最低条件

各ツールは常に次のうち該当する情報を伝える。

1. **今何をつかんでいるか**（面、稜線、頂点、グループ、編集コンテキスト）。
2. **どこに拘束されているか**（軸、面、中点、平行等）。
3. **次に何をするか**（クリック、ドラッグ、数値入力、Enter、Esc）。
4. **確定すると何が変わるか**（追加、切削、面分割、移動、パラメータ更新）。
5. **処理不能ならなぜか**（非平面／非閉合／自己交差／参照面消失等）。

色のみで状態を識別させず、カーソル・ラベル・ハイライト・プレビュー形状を併用する。

## 3. 「線を描く → 面ができる → 面を編集する」をつなぐ

### 3.1 現状からの最重要ギャップ

現行仕様には基本線・矩形・円弧・NURBS曲線、面上作図、開口、押出が存在する。一方、**独立した線と円弧を組み合わせて輪郭を閉じ、面を自動生成する処理**および**既存面を線で分割する処理**は今後の課題とされている。

この2機能は補助機能ではなく、**SketchUpライクな操作感の中核**。ただしBRepの安全性のため、「何でも無条件で面にする」設計にしてはならない。

### 3.2 ワイヤから面への自動生成 — 要件

**対象**：線分・正確な円弧・曲線などで構成される、同一作図コンテキスト内の輪郭。

- F-01 **同一平面性**：点とエッジが許容差内で共通平面上にあり、閉合・非自己交差であれば、ユーザーに面生成コマンドを要求せず面を作る（MUST）。
- F-02 **厳密な曲線の保持**：円弧は円弧、NURBSはNURBSのまま正規輪郭に使う。描画用折れ線をBRepの正規境界に昇格させない（MUST）。
- F-03 **微小ギャップ**：許容差内の接続は安全に統合できる。許容差を超えたギャップは勝手に塞がず、未閉合として表示する（MUST）。許容差の単位と適用範囲を明文化する。
- F-04 **自己交差・重複**：不正な輪郭を黙って修正しない。失敗の位置／理由を示す（MUST）。
- F-05 **複数閉路と穴**：外周・内周の入れ子は妥当性検証後に適切なwire orientationで面を構成する（SHOULD、段階実装可）。重なり関係が曖昧なら拒否する。
- F-06 **非平面閉路**：現時点では自動的な曲面生成をしない。閉じた空間曲線から面を張ることは複数の解があり得るため、意図を問う別機能（Loft/Patch等）へ誘導する（MUST）。
- F-07 **継続性**：面生成後は、選択解除やパネル操作なしにPush/Pullへ移れる（MUST）。
- F-08 **履歴保全**：面生成が複数形状の再構成を伴う場合でも、Undo一回で作図直前の状態に戻れる（MUST）。
- F-09 **編集範囲**：グループ／コンポーネント編集コンテキスト外の同じ座標の線を自動統合しない（MUST）。
- F-10 **オリジナルの作図意図**：編集できるレシピ／輪郭構成情報の保持を優先する。レシピが維持できない場合は、明示的な扱いを設計する（SHOULD）。

### 3.3 既存面への線・曲線入力（面分割）

- 同一平面上で面を横断／閉合する線または曲線について、元の面を**幾何学的に妥当なBRepの面**へ分割できる（MUST、初期対象は平面）。
- 分割後の境界は表示のみの線ではなく、正規BRep上のトポロジーと対応する（MUST）。
- ただし**面上に作図するだけ**の場合と**切削・分割を伴う**場合の違いを、最終操作意図に従い明示しなければならない。ユーザーが予期せずソリッドを切り分けることは禁止。
- 境界が短く途中で止まる、外周に触れる、穴を囲う、既存の辺と重複する等を別ケースでテストする。
- 曲面に描かれた線は、正確な曲面上曲線（p-curve / projected curve等）を成立させる設計が必要。**曲面への一般化は別フェーズ**。平面用処理で擬似的に曲面を切ることはしない。
- ソリッドの一面を分割する場合、分割面と既存隣接面との整合性が維持できる場合にのみ確定する。

### 3.4 アーキテクチャ指針

「線・円弧のスケッチ表現」「閉路／面の生成」「既存面の分割」「最終ソリッドの再生成」を、必要に応じて段階的に分離する。現状の`Recipe`、`Modeler`、`FaceRef`との整合性を確認し、**独立した作図要素が勝手にドキュメント全体のトポロジーを変更しない境界**を明確にする。

推奨の編集パイプライン（実装詳細は検討事項）：

```text
入力（線・円弧・曲線）
  → スナップ／作図面確定
  → 輪郭ネットワークを局所的に評価
  → 閉合・平面性・交差の検証
  → Preview（成立予定の面／分割位置を可視化）
  → Modelerで原子的に確定
  → 正規BRep検証／履歴登録
```

## 4. Push/Pullを「一本の道具」として維持する

### 4.1 ユーザーの意図が先、内部の演算が後

同じ「面をつかんでドラッグ」でも、内部的には押出・レシピ変更・面の再構成・Boolean・曲面オフセットが必要になる。**その差を、必要性がない限りユーザーに選ばせない**。

| 対象／操作 | 期待されるユーザー体験 | 実装上の原則 |
|---|---|---|
| 孤立した平面プロファイルを引く | 立体になる | 既存のパラメトリックExtrudeを活用 |
| 直前に押し出したソリッドの上面を動かす | 高さが変わる | 可能なら元の押出パラメータを更新 |
| ソリッドの側面を動かす | 奥行／幅等が変化する | `FaceRef`の安全性を確認して変更 |
| ソリッド面上の閉輪郭を引く | 凸部を追加 | 妥当な形状に合成、Undoは意図単位 |
| ソリッド面上の閉輪郭を押す | 凹部や開口を作る | 条件に応じて減算／貫通の意味を整理 |
| NURBS等の曲面を押す | 方向・距離・形状が予測できる | 解が一意でない場合は基準方向／厚み定義を明示 |

### 4.2 BRep固有の例外条件

- 曲面のPush/Pullを実装する際、**「法線方向オフセット」「固定方向押出」「境界曲線に沿った変形」**は異なる処理として区別する。UI上は自然な候補を優先し、曖昧なら小さなモード案内を表示する。勝手に推測してモデルを壊さない。
- 開口の「貫通」は厚みの自動認識が必要。途中まで削った凹部と、面の裏側まで抜く切削を混同しない。貫通を示すスナップ／プレビューを用意する（SHOULD）。
- `FaceRef`が再生成後に曖昧／不成立なら**安全に拒否**し、別の面を選んで編集してはならない。長期的に意味付きサブ要素参照へ進化させる。
- ソリッド生成／変更は有効なBRepとして検証し、エラー時は無変更。自動修復をする場合も結果が予測可能で、意図を変えない範囲に限る。
- 出力が複数ソリッドになり得るBooleanは、単一ソリッドの扱いと明確に区別。既存レシピで許容される結果形態を守る。

### 4.3 操作中の軽快さ

Previewは処理の**予測図**でよいが、表示する体積／方向／輪郭は最終演算と整合していなければならない。高負荷時は「簡略プレビュー」と明示。確定で結果が異なる場合は可視化・警告する。粗いテッセレーションを使ってもCADの正本には触れない。

## 5. 推論エンジンは「吸着」ではなく「意図の対話」である

### 5.1 候補生成・選択・説明を分ける

既存の`snap::InferenceEngine`には端点・中点・軸・追跡点・平行・垂直・面上・作業平面等の概念がある。今後、候補種類の拡大だけでなく**候補の安定性と分かりやすさ**を検証する。

- 候補は正規形状から取得し、画面上の距離／可視性／現在の作図コンテキスト／明示ロックを加味して優先する。
- 画面上で近接候補が競合する場合、安易に切り替わらないようヒステリシスを設ける（SHOULD）。スナップの優先順位は明示ロック＞高確度幾何参照＞推定ガイド＞一般の面上／作業平面を基本に設計する。
- 背後に隠れた線・点を通常の操作で誤って吸着しない（MUST）。X-rayなど例外モードは別に設計できる。
- 面上のどの位置で作業しているかが分かり、端点・エッジ・面が重なるとき選択される候補をプレビューできる（MUST）。
- グループ／コンポーネントを編集中は、編集中階層を優先して候補評価する。
- 追跡点・追跡方向はツール間で一貫した寿命・解除条件を持たせる。いつまでも古い補助点が残らない。
- 接線、曲率連続、曲線中心、曲面法線等は将来候補だが、通常の端点・軸スナップを不安定にするなら初期段階では出さない。

### 5.2 UIの可視化

各推論結果は「候補の点／線」「短いテキスト」「確定方向」を一致させる。`Shift`や矢印キーによるロックは画面上でも分かるようにし、制約が解除された時は表示も解除する。数値入力の方向は、ユーザーが見ている制約方向と一致させる。

### 5.3 測定と入力の厳密性

10px前後のスナップ判定（現行実装の参考値）は**入力操作の拾いやすさ**のための画面しきい値であり、BRepの幾何許容差ではない。スクリーン座標とCAD上の数値誤差を混同しない。

## 6. 選択・コンテキスト・部材編集

### 6.1 選択の原則

- 一回クリック＝直接指している面／辺。ダブルクリック＝隣接形状。トリプルクリック＝一体として扱うまとまり（現行仕様を維持）。
- グループ／コンポーネントの外からは全体を選択し、明示的に内部編集へ入る（MUST）。
- 選択済み形状と新しいツールの関係を一貫させる。ツール変更だけでユーザーの意図しない編集対象を選び直さない。
- 左→右の囲み選択は完全包含、右→左は交差対象を含めるルールを推奨（SHOULD）。現行実装を調査し未対応なら提案課題として扱う。
- 表示／非表示、ロック、コンテキスト外の形状は、通常の選択・編集に誤混入しない。
- サブ要素を削除できない場合、無言で親オブジェクトを削除しない。理由と安全な代替操作を示す。

### 6.2 編集階層

通常モードは「建築の形として触る」ことを優先する。必要に応じて段階的に、オブジェクト → 面・辺 → スケッチ輪郭 → 曲線通過点／制御点 → 曲面トリム境界へアクセスできる設計が望ましい。

- **詳細モードの導入が必要な場合も、通常操作は肥大化させない**。
- 制御点などの内部表現の編集と、パラメータを変える編集を区別する。どちらを実行したか履歴とUIで分かるようにする。
- コンポーネント定義編集とインスタンス固有の配置・属性変更を混同しない。「全部変わる」操作はその範囲を可視化する。
- 部材意味論（壁／柱／床／通り芯）を後から導入しても、幾何だけのオブジェクトを操作できる自由さを残す。

## 7. 数値入力は「精密化」であり、別の作業ではない

### 7.1 入力の一貫性

- マウスで大まかな方向・位置を与え、数字を打つと寸法に置き換わる（MUST）。
- 現在の操作が数値を何として解釈するか（距離、角度、半径、X/Y寸法、オフセット、複製数）を状態ヒントで表示する（MUST）。
- `3000`、`4.5m`、`4000,6000`、`x4`、`/4`等の既存文法は維持。数字だけでmm、角度は度、Z上方向を基準にする。
- 直後の再入力は、可能な限り**直前操作のパラメータ修正**とし、無関係な新しい編集を生成しない（MUST）。どのタイミングで直前操作が無効になるかを明文化する。
  - **実装済みの共通契約（`app::RecentEdit`、全ツール共通）**：直前操作が「直後」なのは、その後モデルが一切変わっていない（他の編集・Undo・Redo・AI の書き込みがない）間だけ、かつ同じツールのまま。カメラ操作・選択・AI の読み取りでは失われない。ツールを切り替えた時点で無効
  - 再入力は直前操作と**同じ 1 つの Undo ステップ**に入る（`CommandStack::beginAmend`）。何度打ち直しても Ctrl+Z 1 回で操作ごと戻る
  - 置き直し型（移動・回転のコピー/配列、尺度、開口）は「直前を取り消して新しい値でやり直す」を 1 ステップで行い、新しい値が失敗したら元の操作が戻る（以前は元の操作が消えたままになり得た）
  - 対象：円・多角形・矩形・円弧・寸法・テキスト・プッシュ/プル・オフセット・回転体・移動・回転・尺度・開口。テスト `typedRevisionOnlyRightAfter`
- 負値、ゼロ、微小値、桁区切り、単位混在、IME入力、数値ボックスへフォーカス中のショートカットをテストする。
- 複数値の区切り文字と小数点はロケールにより衝突し得る。日本語Windows上の標準書式を明示し、曖昧値は誤解釈せず拒否する。
- GUIとMCPで入力の文法は違ってもよい（GUIは`4.5m`、APIはmm実数）が、内部に入る**寸法意味論・単位変換・検証結果は一致**させる。

### 7.2 後から変更できることを資産にする

モデルが単なる最終BRepでなく、`Recipe`で寸法・配列・開口・ロフト等の由来を保持できる場合、右パネルから再編集できることを優先する。編集履歴の表示は主画面に押しつけず、必要時に展開する。

すべてを無理にパラメトリック化する必要はない。ただし、パラメータを失う操作は可能な範囲でユーザーに分かるようにする（SHOULD）。

## 8. カメラ・操作速度・画面構成

### 8.1 視点移動の契約

- ホイールズーム、オービット、パンを作図ツール使用中にも提供する（MUST）。
- カーソル位置中心のズーム／オービットが実用的に動くこと（現行思想を維持）。
- 遠景の建物全体から建具のディテールまで、極端なズームでスナップや描画が不安定にならないようにする。
- 透視／平行投影の切替、シーン呼び出しの前後で予期しない形状更新がない。
- Sceneはビューの保存を主目的とし、形状変更履歴やAI操作と混同しない。

### 8.2 応答性能の評価方法

ハードウェア・OCCT形状の複雑さに依存するため、以下は**初期の設計目標（合否基準ではない）**。現行のターゲットマシンで計測して予算を再設定する。

| 操作 | 暫定UX目標 | 超えた際の対応 |
|---|---|---|
| ホバー候補更新 | 通常モデルで知覚できる遅れを避ける（参考：50ms程度以内） | 候補探索の段階化／キャッシュ |
| ドラッグ時のプレビュー | 可能なら30fps以上、操作の追従を優先 | 簡略プレビュー／重い演算の非同期化 |
| 形状確定 | 重い処理は進行状況と中断手段を検討 | 操作不能の無表示フリーズを避ける |
| Undo/Redo | 体感的に即時の復帰を目指す | スナップショット管理や表示更新を分析 |

**性能を上げるために正規BRepを粗い三角メッシュへ置き換えてはならない。**

### 8.3 UIの密度

基本ツール／数値入力／ステータス／シーンを優先し、詳細プロパティ・形状内部構造・専門的オプションは必要に応じて表示する。高機能化を、ツールバーの無秩序な追加で表現しない。頻用操作を浅く、専門操作を深く配置する。

## 9. AI共存のUX：GUIとAIは「同じ設計者の手」

### 9.1 共通意味論

`doc::Modeler`を編集の唯一の権威ある経路とする既存方針を守る。MCP/CLIや将来のアプリ内チャットは、幾何検証・履歴・権限の別系統を持たない。

- AIも、取得した**選択状態、対象の属するコンテキスト、面・辺の参照状態**を守る。
- GUIとAIの同等操作で、許容誤差内の幾何結果と同じロールバック保証を得られる（MUST）。
- ドキュメント改変APIと読み取りAPIを明確に分離する。
- AIに成功を報告するのは、**コマンド実行とモデルの検証が成功した後**だけ。
- アプリ連携は現在の既定OFF／同一ユーザー通信／アプリ経由のファイル操作禁止を維持。提案プレビュー導入時もバイパスしない。

### 9.2 「AIが提案するが、ユーザーが確定する」

半透明プレビュー（将来実装）では、次の契約を守る。

1. AIは処理案を**同じコマンド形式**で提出する。
2. 検証可能な一時ドキュメント／スナップショットに案を適用し、プレビューを生成。
3. GUI上で変更対象・追加／削除・主要寸法・失敗理由を表示。
4. ユーザーは「適用／却下」を選べる。却下は正規ドキュメントに副作用を残さない。
5. 適用時は編集元のリビジョンが変わっていないか確認し、変化した場合は再検証する。旧案を無条件適用しない。
6. 適用は原子的な1履歴単位。失敗は全ロールバック。

現段階では、この機能を実装したと誤認しない。まず「プレビューに必要な**純粋なコマンド計画／適用／検証**の境界」が現行構造で実現可能か設計評価する。

### 9.3 AIの「見る」と「理解する」を混同しない

`capture_view`は見た目の理解に便利だが、幾何の真偽判定は`get_object`等の数値・BRep情報に基づいて行う。画像から推測した寸法を正確なCAD値として使用しない。面参照が再計算で失効した場合は再取得する。

将来の意味的なサブ要素参照（例：「屋根の上面」「通り芯X3に沿う面」）は、番号や法線だけに依存する参照より堅牢にするための設計課題であり、機械学習によるラベル推測だけに任せない。対応するトポロジー追跡と検証が必要。

## 10. 失敗体験の設計

以下を**必ず分けて通知**する。

| 失敗分類 | 例 | 振る舞い |
|---|---|---|
| 入力未確定 | 線が閉じていない | 作図を継続可能、閉合不足を可視化 |
| 幾何的に不正 | 自己交差／厚みゼロ | 未変更、どの位置が不正か説明 |
| 解が曖昧 | 非平面閉路から面を張る | 暗黙実行せず適切な別操作へ誘導 |
| トポロジー参照失効 | 上流レシピ変更後のFaceRef | 取り違えて変更しない、再選択を促す |
| 許可なし | AI連携OFF／禁止ファイル操作 | 変更なし、必要な許可の種類を説明 |
| 性能・中断 | 重いBoolean、ユーザーが取消 | 中間形状を正規ドキュメントに残さない |

エラーメッセージは「内部の例外名」だけで終えず、「操作できなかった理由／モデルは変更されていない／次にできること」を短く伝える。

## 12. 段階的な実装計画：機能数より操作の連続性

| 段階 | 目的 | 推奨成果物 | 完了条件 |
|---|---|---|---|
| **Gate 0：基準固め** | 現行の操作感を測り、原則とのギャップを確定 | 操作契約一覧、既存コード対応表、建築シナリオ録画 | 変更対象と回帰対象が明確 |
| **Gate 1：描画→面→立体** | 閉合面生成と既存面分割を成立させる | 輪郭処理・分割・正規BRep検証・Undo・テスト | AC-03〜09が通る |
| **Gate 2：入力体験の統一** | 推論・選択・数値・Esc・カメラの一貫性を高める | 共通操作ルール、状態表示、回帰／E2E | AC-10〜15、22を評価 |
| **Gate 3：BRepならではの直接編集** | 曲面にも直感的操作を展開 | 曲面プレビュー、法線／方向規則、TNP強化 | 失敗時安全性と精密性を守る |
| **Gate 4：AI共同操作** | GUIとAIの同等性を高める | 提案プレビュー、差分表示、リビジョン確認 | AC-16〜20を満たす |

注意：この順番は思想上の**依存関係**であり、既存のPhase 3（3DM、曲面Push/Pull等）を即座に停止しろという命令ではない。寸法線／テキストは調査時点で実装記載があるため、まずUX回帰評価の対象とする。

### 12.1 今やらないこと（明確な非目標）

- GUIを模倣するためのポリゴン主体への設計変更。
- すべての形状編集を一度に完全パラメトリック化すること。
- 非平面の任意閉路から、無条件に「適当な曲面」を自動生成すること。
- すべてのRhino機能をツールバーへ並べること。
- AIのためだけの編集ロジック／Undo機構／ファイル権限の抜け道。
- BRepの不正を静かに形状修正して「成功」と返すこと。
- 高速化のために保存精度と表示品質を結合すること。

## 13. 実装時に必ず答える設計上の論点

1. **作図要素の所有者**：既存面を分割する入力線は、作図中・確定後・分割後にどのオブジェクト／レシピへ属するか。
2. **スケッチとBRepの境界**：wireの閉合後、いつfaceとして扱い、どの操作を原子的Undoにまとめるか。
3. **スプリット後のID**：分割した面の選択・FaceRef・履歴はどう追跡されるか。TNPの安全な代替は何か。
4. **同一平面上の重複輪郭**：複数の共有エッジ、穴、多重ループ、ほぼ接する円弧をどう扱うか。
5. **平面上の閉輪郭とソリッド切削**：作図直後に面が追加されることとソリッドへBooleanすることの所有権・タイミングをどう分けるか。
6. **プレビューの妥当性**：プレビューと確定計算が異なるケースの表示規則は何か。
7. **Ctrl/Esc/数値の衝突**：ツールごとに意味が異なる修飾キーやIME入力を、ユーザーにどう説明するか。
8. **AIとの競合**：操作途中のAIコマンドがキャンセルされる現行仕様に、プレビュー段階を導入するときの変更衝突をどう扱うか。
9. **巨大モデル**：複数の高層建築／複雑な曲面でUI性能が落ちた場合、何を近似し、何を決して近似しないか。
10. **建築部材への発展**：壁、柱、開口、通り芯等の意味づけが幾何操作を強制しない設計になっているか。

### 最後に

> SketchBRepは「難しい幾何演算を知っている人だけが使えるCAD」になってはならない。
> 
> **簡単な操作から高度な幾何へ辿り着けること。**
> 
> そのために、複雑な計算やトポロジーの制約はエンジン側で引き受ける。ただし、曖昧さや失敗は隠さず伝え、ユーザーのモデルを守る。
> 
> 人間は形を触り、AIは形を理解し、両者が同じ正規BRepと同じ編集履歴を共有する。
> 
> **それがSketchBRepの存在理由である。**
