# 曲面を線で分割できない問題の調査（2026-10-26 JST）

## 依頼と結論

ユーザー依頼：画像の曲面が線で分割されない件について、改修のハードルと大量処理時の負荷を確認し、どちらも問題なさそうなら反映する。
追加回答：縦線は線ツール、横線は上部の円弧をコピー・ペーストしたもの。

**アプリへの反映は保留。** 円筒に正確に重なる直線・円を刻む処理自体は可能で、少量なら軽い。
しかし大量の縦横分割では面数が掛け算で増え、まとめて計算する試作でも待ち時間が出た。
「大量処理でも問題なさそう」という反映条件には、現時点では達していない。
今回は調査記録と再現用ベンチマークのみ追加し、製品の分割動作・保存形式・Windows EXEは変更していない。

## 原因と改修範囲

- `Modeler::lineCrossesFace` が非平面を候補から除外する。
- `geom::pointOnFace` / `pointOnFaceBoundary` も平面専用。
- 分割履歴の `SplitOp` は平面の `FaceRef` を保存する。
- 貼り付けた円弧は、平面の線分割が使う `worldPolyline` の対象でもない。

したがって、表示の線が曲面のトポロジー上の境界になる処理がない。
平面判定を1箇所外すだけでは、コピー円弧・保存再読込・履歴・面選択まで対応できない。
画像の円筒に限定した改修は中程度。任意のNURBS曲面へ線を投影する汎用機能は別の大きな改修になる。
直線の両端が曲面上にあっても、その間の直線が曲面内部の弦なら、曲面上の線とはならない。
投影方法や分割対象の扱いを勝手に決めてはならない。

## 試作と測定条件

半径1000 mm・高さ3000 mmの閉じた円筒を生成。
縦線は側面の母線、横線は上端の円を高さ方向に移したものと同じ正確な円を使用。
元モデルは未提供のため、画像に対応する理想円筒でのカーネル試作であり、元の `.sbr` を使ったGUIの再現テストではない。

OCCTの一括分割 `BRepAlgoAPI_Splitter` で、円筒を引数、全縦線・円を工具として同時に処理する。
各結果について、期待する格子数、閉じた立体が1つであること、B-repの正当性、面積・体積の維持を確認した。

環境：クラウド Linux / GCC 14.2 / OCCT 7.8.1 / Release。各条件3回の中央値。
時間は分割、形状検証、面積・体積照合の合計。描画、マウス選択、素材再配置、履歴の保存・再読込は含まない。
Windows実機の計測値ではない。

全18回で面数・立体の正当性の検証に合格。
面積と体積の相対誤差は最大でも1e-8の検証基準を十分下回った（生CSV参照）。
縦n本・横m本では、側面だけで `(n+1)*(m+1)` 区画になる。
分割線が増えるだけの問題ではなく、表示・選択・保存が扱う面も増える。

上記は同じ1個の円筒を密に分割する試験。別々の円筒に少数ずつ分割した場合の応答時間とは区別する。
正確な区画を作れることは確認できたが、上記の待ち時間を許容して自動反映する判断はしない。

## 次の実装に必要なこと

- 面上の線を対象とした曲面刻印と、コピー円弧の貼り付け経路を共通化する。
- 過去の分割を1件ずつ全再実行せず、一括計算・結果の再利用を組み合わせる。
- ホバー中に重い分割を走らせない。大きな分割は処理を明示し、UIの応答・中止にも対応する。
- 面の同一性、分割後の素材、Undo/Redo、保存再読込、曲面の押し引きとの組み合わせを検証する。
- 多数のオブジェクトのうち一部だけを分割する場合も、離れた形状を高コストな候補探索へ入れない。

## 再現

製品本体から独立した調査用コード：`docs/repro/curved_split`。
既存のOCCT開発環境で実行できる。アプリのCMakeには接続しておらず、通常ビルドや配布物には含めない。

```sh
cmake -S docs/repro/curved_split -B build/curved-split-probe -DCMAKE_BUILD_TYPE=Release
cmake --build build/curved-split-probe --config Release
build/curved-split-probe/curved_split_probe 3
```

Windowsの複数構成ジェネレーターの場合は `build/curved-split-probe/Release/curved_split_probe.exe 3`。
