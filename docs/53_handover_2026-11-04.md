## 2. 守ること（オーナーの決まり）

- 同じブランチで作業する。amend・rebase・force-push はしない。main へはマージしない。
- 有料の AI API や重い処理を前提にしない。
- 資格情報や、期限のある URL を文書に書かない。
- オーナーの非公開 DXF（約 20MB）は、リポジトリにも配布物にも入れない。
- Jw_cad の付属サンプル（.jww）はリポジトリに入れない（テストは環境変数 `SBR_JWW_SAMPLES` がある時だけ動く）。
- **SketchUp SDK のファイルは、Trimble から書面の許可が来るまで、どこにも置かない。**
- 操作は SketchUp のように直感的に。ルールで人の操作を止めない。
- 確認は 3 段階に分けて報告する：**計算テスト済み / GUI 自動確認済み / Windows 実機確認**。実機で確かめていないことを「確認済み」と書かない。
- CI が緑になったら、Windows の zip（とインストーラー）をオーナーに渡す。
- オーナーへの報告は日本語。専門用語はかみくだく。何をして、何を決めたかを必ず書く。

## 3. ビルドとテスト

```bash
# Linux（Ubuntu 24.04、Qt 6.4、OCCT 7.x、apt のパッケージ。CI の linux ジョブと同じ）
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
ninja -C build
# GUI テストは X が要る
Xvfb :99 -screen 0 1920x1080x24 &
DISPLAY=:99 ctest --test-dir build -j4 --timeout 1500   # 452 本。gui ラベルの 4 本が重い
# 1 つだけ
DISPLAY=:99 build/tests/sbr_gui_tests helpWindowAndCrashLog
```

- `QT_QPA_PLATFORM=offscreen` では GUI テストが止まる（OCCT のビューアが X11 を要る）。必ず Xvfb。
- Windows は CI（`.github/workflows/ci.yml`）で、conda-forge の OCCT 8 / Qt 6 を使う。OCCT 7 と 8 で API の違いがある（例：`DynamicType` が無い → `typeid` を使う、`KernelError.h`）。MSVC では `near` などがマクロ。
- CI の Windows ジョブ：ビルド → コアのテスト → zip の作成 → ライセンス収集 → DLL の確認 → 起動の確認 → **インストーラー（Inno Setup）の作成と、静かにインストール・アンインストールの確認** → GUI テスト（Mesa のソフトウェア OpenGL、画面 1920×1080）。
- 成果物：`SketchBRep-windows-x64`（zip のフォルダ）、`SketchBRep-windows-x64-setup`（`SketchBRep-0.1.0-setup-x64.exe`）、`windows-gui-test-log`。
- CI の節約モードについては docs/09。

## 5. 次にやること：構造種別の手引き（docs/52）

**設計は docs/52 で決まっている。まず段階 1 から。** オーナーと決めたこと：

- 木造の標準寸法は市場の流通寸法（docs/52 §4.1）。事務所の標準は無い。
- 最初のレシピは **2 階建て**（平屋は「2 階なし」）。
- **壁量計算は枠を作り、係数表を同梱する。** 結果には必ず「いつ時点の基準か」の但し書きを出す（docs/52 §7.3）。表の値は原典で 1 つずつ確かめてから入れ、確かめられない値は入れずに未評価にする。
- **金物は形として置く**（共有の部品・簡略形、docs/52 §5.1）。重ければ目印方式に切り替える。
- RC の配筋はやらない。
- 最終的に木造・鉄骨造・RC 造の「手引き」を同じ仕組みで作り、人と AI に同じデータから説明を渡す。

### 段階 1 の作業（目安）

1. `assets/construction/timber/` に JSON：断面カタログ（`source`・`normative` つき）、役割の一覧と既定の断面、プリセット（モジュール・基準高さ）。鉄骨の `assets/steel_sections.json` と同じ読み込みの仕組みに揃える（`src/core/include/sbr/geom/Section.h` と、鋼材カタログを読む所を参照）。
2. 利用者の上書き（PC の設定 or プロジェクト）を、元の表とは別に保存する。
3. 役割は既存の属性 `kind`、材料は `material_class`（steel / timber / rc）を使う。新しい項目は増やさない（docs/40 §の方針）。
4. AI のコマンド：既存の `list_sections`（`src/core/src/CommandApi.cpp`、鋼材カタログの検索）に `system`・`role` を足して木の断面も返す。`get_construction_guide {system}` を新しく足す。鋼材カタログの元データは `tools/import_steel_catalog.py` で作っている。MCP の説明（`src/core/src/McpServer.cpp` の `instructions()`）に「構造種別の手引きを先に読む」を足す。
5. 手引きの文章はデータから作る。ヘルプのトピック（`src/app/HelpWindow.cpp` の `kTopics`）にも出す。
6. テスト：カタログの読み込み、上書き、AI から木の断面を選んで柱を引く、手引きにカタログの値が出る。

段階 2 以降（レシピ、チェック、拾い出し・伏図、壁量、鉄骨・RC）は docs/52 §11 の表のとおり。
