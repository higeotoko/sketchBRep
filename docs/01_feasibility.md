# 01. 技術的成立性・難易度・代替案の分析

開発開始時の分析結果。結論から言うと **仕様書の第一候補（C++ / OCCT / Qt 6）で成立する**。
Phase 0〜1 のプロトタイプで実際に成立を確認済み（[03_phase0-1_report.md](03_phase0-1_report.md)）。

## 1. 要素ごとの成立性と難易度

| 要素 | 成立性 | 難易度 | 根拠・所見 |
|---|---|---|---|
| B-rep 生成（矩形→押出） | ◎ | 低 | `BRepBuilderAPI_MakeFace` + `BRepPrimAPI_MakePrism`。体積が解析値と一致（相対誤差 0） |
| B-rep 妥当性検証 | ◎ | 低 | `BRepCheck_Analyzer` + シェル閉合 + 体積符号で「不正ソリッドを成功扱いしない」を担保 |
| STEP 入出力 | ◎ | 低 | `STEPControl_Writer/Reader`（AP214, mm）。往復で寸法誤差 1e-6 mm 以内 |
| ビューポート（Qt 6 + OCCT） | ○ | 中 | ネイティブウィンドウハンドルを `WNT_Window` / `Xw_Window` に渡す定番構成。HiDPI 換算に注意 |
| 選択（面ピック） | ○ | 中 | AIS の面選択モード。**OCCT 7.6 では選択モード -1 で表示したオブジェクトが後から選択不能**になる罠を確認・回避済み |
| スナップ・推論 | ○ | 中 | CAD 形状（頂点・エッジ曲線・面）から評価し画面距離で判定。GUI 非依存で単体テスト可能 |
| Push/Pull（平面プロファイル） | ◎ | 低 | 押出パラメータとして保持 |
| Push/Pull（ソリッドの平面フェース） | ○ | 中〜高 | 面プリズムとの Fuse/Cut + `ShapeUpgrade_UnifySameDomain`。結果が単一の有効ソリッドでなければ失敗としてロールバック |
| パラメトリック再編集 | ○ | 高 | レシピ（ベース形状 + 修飾操作列）を保持し全再計算。**Topological Naming Problem が本質的難所** |
| Undo/Redo | ◎ | 低 | オブジェクトスナップショット方式（OCCT 形状は参照カウントなので安価） |
| ネイティブ保存 | ◎ | 低 | JSON（レシピ・属性）+ ジオメトリのみの BRep テキスト。原子的保存 + 再読込検証 |
| 3DM 連携（Phase 3） | △ | 高 | openNURBS ↔ OCCT 変換は自前実装が必要。トリム曲面・単位・許容差の対応付けが課題 |
| 大規模建築モデル | △ | 高 | AIS は数万オブジェクトで重くなる。インスタンス描画・LOD は将来カスタムレンダラを検討 |

## 2. 最大の技術リスク

1. **Topological Naming Problem（TNP）**
   再計算でフェースの番号・実体が変わるため、履歴が「どの面」を参照しているかを安定に保てない。
   - 本実装の対策: 面を配列番号ではなく **幾何シグネチャ（外向き法線・支持平面・重心）** で参照し、再計算後に幾何マッチで解決（`geom::FaceRef`）。
   - 解決できない場合は **編集を拒否して元の形状を保持**（黙って壊れた形状にしない）。テストで挙動を固定済み。
   - 次段階: 押出の生成履歴（`BRepPrimAPI_MakePrism::Generated` / Boolean の `Modified`）を使った意味的命名（"Extrude.top", "Extrude.side[i]"）とのハイブリッド。
2. **B-rep に対する SketchUp 的直接編集の一般化**
   ポリゴンなら頂点移動で済む操作が、B-rep では Boolean・面統合・トリムの再計算になる。
   曲面・非平面・自己交差を伴う編集は段階的に対応範囲を広げる方針（仕様書どおり）。
3. **OCCT Visualization の性能上限**
   建築規模（数万部材）では AIS ベースの表示がボトルネックになりうる。表示層はコアから分離してあるので、
   将来 `display::DisplayMesh` を使った独自レンダラ（インスタンシング・LOD）に差し替え可能。

## 3. 代替案の比較

### CAD カーネル

| 候補 | 長所 | 短所 | 判定 |
|---|---|---|---|
| **Open CASCADE (OCCT)** | OSS（LGPL）、B-rep/NURBS/Boolean/フィレット/STEP 一式、実績多数 | Boolean・フィレットの堅牢性は商用に劣る、API が古風 | **採用** |
| Parasolid / ACIS | 業界標準の堅牢性 | 高額ライセンス、個人・小規模開発では非現実的 | 将来の差し替え候補として抽象化のみ意識 |
| C3D Toolkit | 商用としては比較的安価、直接編集に強い | 商用契約が必要 | 代替候補 |
| openNURBS 単体 | Rhino 互換 | 幾何アルゴリズム（Boolean 等）を持たない | 3DM 入出力専用で併用 |
| 自前 NURBS エンジン | 完全な制御 | 工数が桁違い | 仕様どおり初期目標外 |
| メッシュカーネル（Manifold, CGAL） | Boolean が高速・堅牢 | 正規形状がポリゴンになり基本思想に反する | 不採用 |

### GUI / 描画

| 候補 | 判定 |
|---|---|
| **Qt 6 Widgets + OCCT AIS/V3d** | 採用。最短で選択・ハイライト・シェーディングが揃う |
| Qt Quick (QML) + OCCT | タッチ・アニメーションは得意だが OCCT 埋め込みの事例が少なく初期リスク大 |
| Dear ImGui + 独自 OpenGL | 軽量だがドッキング UI・多言語入力・ダイアログを自作する必要 |
| 独自レンダラ（OpenGL/Vulkan/D3D12） | 大規模モデル向けに将来検討。表示層を分離済みなので段階的移行が可能 |

### 言語

C++17 を採用（OCCT・Qt がネイティブ C++）。Python バインディング（pythonocc）での試作も可能だが、
配布性能と型安全性の観点で本体は C++。AI/スクリプト API は将来 `doc::Modeler` を薄くラップする形で提供する。

## 4. ライセンス

- **OCCT**: LGPL 2.1 + OCCT 例外。動的リンクで利用し、OCCT 自体を改変した場合はその改変を公開する。
- **Qt 6**: LGPL 3（または商用）。LGPL で配布する場合、ユーザーが Qt を差し替え可能な形（動的リンク）にする。
- **openNURBS**（Phase 3）: 独自の寛容ライセンス。
- **nlohmann-json**, **GoogleTest**: MIT / BSD。

商用配布を視野に入れる場合は、上記 LGPL 条件（動的リンク・再リンク可能性・ライセンス文書同梱）をビルド・インストーラ設計に組み込むこと。

## 5. 結論

- 「Rhino の精度で保存される直方体を、SketchUp のような操作で生成する」は **OCCT + Qt 6 で達成可能**であり、プロトタイプで達成した。
- 最重要の研究課題は TNP と B-rep 直接編集の一般化。アーキテクチャ上、レシピ（Document）と形状（Geometry）と表示（Display）を分離したことで、これらの改良をコアに閉じて進められる。
