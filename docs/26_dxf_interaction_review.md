# 大規模 DXF の操作性能精査（2026-10-26 JST）

## 対象と手順

ユーザーから「カクカクして動かせない状態が残らないか精査」と依頼。
提供された約20 MBの実 DXF（取り込み可能な線図35,880本、レイヤ別141オブジェクト）を使用した。
元ファイルはリポジトリにも配布物にも含めない。

`SBR_DXF_BENCH` に実ファイルのパスを指定し、`sbr_drawing_import_tests largeDrawingUsesLayerBatches` を実行。
ズーム10回、画面上の8×5点でスナップ・辺選択・オブジェクト選択・選択ツールのホバー・回転・平行移動・線ツールのホバーを計測する。
全選択、全体移動、Undoも確認する。各点の時間は処理呼び出しの経過時間で、描画を伴う操作にはQtイベント処理も含む。
環境はクラウドの Xvfb / ソフトウェア描画。Windows実GPUでの実測ではない。

## 見つかった問題と修正

### レイヤをまとめた図面を移動すると失敗する

実ファイルを全体移動すると `Line has coincident consecutive points` で失敗した。
通常の作図線向けの重なり整理が、独立した多数の線を持つ ImportedShape の Compound を単一の線図として扱っていた。
この処理には重なった線を削除・分割・再作成する副作用もあった。

- 曲線の ImportedShape Compound は、配置変更後の自動整理の対象から除く。
- 新しく描く線の端点によって、取り込み済みのレイヤ全体を分割・再作成する処理も避ける。
- 重なり、正確な曲線、元レシピ、IDを保持する。通常の作図線の整理は継続する。
- 重なる線を持つ別レイヤの移動、形状・ID保持、Undo/Redoを回帰テストで確認。
- 実図面の全体移動も成功し、表示更新まで約99 msだった。

### マウス操作中の描画負荷

通常画質の4倍MSAA等の輪郭平滑化を全フレームに使い、ソフトウェア描画では回転の中央値が約129 ms/フレームだった。

- マウス移動・カメラ操作中だけ輪郭平滑化を抑える。辺や面を省略せず、幾何形状も近似し直さない。
- 入力が止まって180 ms後に通常画質へ戻す。カメラのドラッグ中は戻さない。
- 画像書き出しは、操作中でも通常画質に戻してから行う。
- ズーム・ドラッグ・停止後の復帰と、画像書き出し時の復帰をGUIテストで確認。

## 最終の実図面計測

| 操作 | 中央値 ms | 95パーセンタイル ms | 最大 ms |
|---|---:|---:|---:|
| スナップ | 1.70 | 30.29 | 72.48 |
| 辺選択判定 | 0.036 | 0.57 | 9.27 |
| オブジェクト選択判定 | 0.038 | 0.18 | 10.37 |
| 選択ツールのマウス移動 | 41.78 | 65.98 | 168.80 |
| 回転と再描画 | 18.01 | 19.30 | 21.20 |
| 平行移動と再描画 | 34.73 | 37.42 | 59.56 |
| 線ツールのマウス移動 | 38.82 | 63.81 | 217.38 |

- 取り込み・表示：約3.56秒。
- ズームと再描画10回：約229 ms（対策前：約1159 ms）。
- 回転開始のスナップ：約8 ms。
- 全選択・表示更新：約34 ms。
- 全体移動・表示更新：約99 ms。
- ログ：`/tmp/sbr-interaction-full-before.log`、`/tmp/sbr-interaction-final.log`。

この範囲では操作不能や数秒単位の停止は再現しなかった。
ただし初回のキャッシュ作成や通常画質への復帰等では100〜220 ms程度の引っ掛かりがあり、全操作が常に滑らかとは断言しない。
40点の計測で全画面・全倍率・全GPUを網羅したものでもない。Windows実機の速度は未確認。
文字・寸法・ハッチなどの未対応要素は今回の操作性能とは別の制限として残る。
